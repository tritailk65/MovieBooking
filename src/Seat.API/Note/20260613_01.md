Có. Với code hiện tại, mình nghĩ Seat service nên tách rõ 2 pha: **initial snapshot để render nhanh** và **delta realtime để cập nhật trạng thái**.

Hiện tại endpoint ở [SeatEndpoints.cs](/Users/tari/Project/Microservice_Learning/MovieBooking/Seat.API/Apis/Endpoints/SeatEndpoints.cs:14) chỉ có:

`GET /api/v1/seat/{showtimeId}/seats`

và DTO mới trả `SeatId`, nên client chưa đủ dữ liệu để dựng sơ đồ ghế tử tế.

**Nên thêm các endpoint chính này:**

```http
GET /api/v1/showtimes/{showtimeId}/seat-map
```

Dùng cho lần render đầu. Response nên có cả layout + status:

```json
{
  "showtimeId": 123,
  "hallId": 5,
  "version": 42,
  "serverTime": "2026-06-13T10:00:00Z",
  "lockDurationSeconds": 600,
  "rows": [
    {
      "row": "A",
      "seats": [
        {
          "seatId": "A1",
          "row": "A",
          "number": 1,
          "type": "Standard",
          "price": 90000,
          "status": "Available",
          "lockedUntil": null
        }
      ]
    }
  ]
}
```

Client chỉ gọi endpoint này một lần khi mở màn chọn ghế. Nếu layout không đổi, có thể cache mạnh bằng `ETag` hoặc chia thành `layoutVersion` và `statusVersion`.

```http
GET /api/v1/showtimes/{showtimeId}/seat-status
```

Dùng khi client đã có layout cache rồi, chỉ cần status nhẹ:

```json
{
  "showtimeId": 123,
  "version": 43,
  "seats": [
    { "seatId": "A1", "status": "Available" },
    { "seatId": "A2", "status": "Locked", "lockedUntil": "..." },
    { "seatId": "A3", "status": "Sold" }
  ]
}
```

```http
POST /api/v1/showtimes/{showtimeId}/seats/locks
```

Nên hỗ trợ lock nhiều ghế một lần thay vì chỉ một ghế:

```json
{
  "seatIds": ["A1", "A2"]
}
```

Response:

```json
{
  "success": true,
  "reservationId": "res_...",
  "lockToken": "...",
  "lockedUntil": "2026-06-13T10:10:00Z",
  "seats": ["A1", "A2"],
  "version": 44
}
```

Nếu một ghế bị người khác lock/sold thì trả `409 Conflict` kèm danh sách ghế fail.

```http
DELETE /api/v1/showtimes/{showtimeId}/seats/locks/{reservationId}
```

Release toàn bộ ghế user đã giữ khi back khỏi checkout hoặc đổi lựa chọn.

```http
PATCH /api/v1/showtimes/{showtimeId}/seats/locks/{reservationId}/renew
```

Gia hạn lock nếu user vẫn đang checkout. Không bắt buộc ngay, nhưng thực tế rất hữu ích.

**Realtime nên dùng SignalR:**

```http
/ws/seat-hub
```

Client join group theo showtime:

```text
JoinShowtime(showtimeId)
LeaveShowtime(showtimeId)
```

Server push event dạng delta:

```json
{
  "type": "SeatStatusChanged",
  "showtimeId": 123,
  "version": 45,
  "changes": [
    {
      "seatId": "A1",
      "status": "Locked",
      "lockedUntil": "2026-06-13T10:10:00Z"
    }
  ]
}
```

Các event nên push sau `lock`, `release`, `sold`, và khi lock expire. Nếu chưa muốn đưa SignalR vào ngay thì fallback hợp lý là:

```http
GET /api/v1/showtimes/{showtimeId}/seat-events?afterVersion=44
```

hoặc polling:

```http
GET /api/v1/showtimes/{showtimeId}/seat-status?afterVersion=44
```

**Một điểm quan trọng trong code hiện tại:** lock Redis có TTL, nhưng hash `showtime:{id}:seats` vẫn được set `SeatStatus = Locked` trong [LockSeatCommandHandler.cs](/Users/tari/Project/Microservice_Learning/MovieBooking/Seat.API/Application/Seats/Commands/LockSeat/LockSeatCommandHandler.cs:49). Khi lock key hết hạn, snapshot có nguy cơ vẫn trả ghế là `Locked`. Vì vậy endpoint `seat-map` / `seat-status` nên normalize trạng thái: nếu `Locked` mà `LockExpiration < serverTime` hoặc lock key không còn tồn tại thì trả `Available` và tốt hơn là cleanup hash.

Tóm lại, bộ tối thiểu mình sẽ chọn là:

```http
GET    /api/v1/showtimes/{showtimeId}/seat-map
GET    /api/v1/showtimes/{showtimeId}/seat-status
POST   /api/v1/showtimes/{showtimeId}/seats/locks
DELETE /api/v1/showtimes/{showtimeId}/seats/locks/{reservationId}
PATCH  /api/v1/showtimes/{showtimeId}/seats/locks/{reservationId}/renew
/ws/seat-hub
```

Còn các endpoint kiểu `markseatsold` nên để internal/event handler từ Booking service gọi qua integration event, không nên public cho client.
