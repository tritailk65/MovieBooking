như vậy sẽ có key, thứ nhất là showtime dùng để trả về cho người dùng sơ đồ ghế kèm theo là trạng thái ghế với tốc độ phải nhanh và gần như realtime, thứ 2 là lock key, dùng để chống race condition giữa nhiều user trở lên, và thứ 3 là reservation key, dùng để gom cụm ghế theo user id để phục vụ cho việc trả về dữ liệu seat đã order cho booking service và clean các ghế bị lock khi order thành công hoặc cancel

Đúng rồi. Cách bạn tổng kết là **chuẩn kiến trúc hơn** cho Seat Service:

```text
1. showtime seat map key
2. per-seat lock key
3. reservation key
```

Vai trò nên tách như này:

```text
showtime:{showtimeId}:seats
```

Dùng để render sơ đồ ghế nhanh cho frontend. Đây là read model/cache. Có thể chứa `Available`, `Locked`, `Sold`, `LockedByUserId`, `LockExpiration` nếu cần UI hiển thị countdown. Nhưng không nên coi nó là nguồn chống race chính.

```text
lock:showtime:{showtimeId}:seat:{seatId}
```

Dùng để chống race condition. Mỗi ghế một lock key, set bằng `SET NX EX`. Ai set thành công thì giữ được ghế. Đây là lớp bảo vệ quan trọng nhất để không có 2 user cùng giữ một ghế.

```text
reservation:{reservationId}
```

Hoặc nếu mỗi user chỉ có một reservation trên một showtime:

```text
reservation:showtime:{showtimeId}:user:{userId}
```

Dùng để gom các ghế user đang giữ:

```json
{
  "reservationId": "...",
  "userId": "u1",
  "showtimeId": 100,
  "seatIds": ["A1", "A2"],
  "expiresAt": "..."
}
```

Key này phục vụ rất tốt cho:

```text
GET selected seats by user
Send selected seats to Booking Service
Release all seats when cancel/payment failed
Mark all seats sold when payment/order success
Refresh TTL when user adds another seat
```

Flow chuẩn sẽ là:

```text
User chọn ghế
-> acquire per-seat lock key
-> add seat vào reservation
-> update showtime seat map thành Locked
```

User thêm ghế:

```text
-> kiểm tra reservation còn sống
-> lock ghế mới
-> add vào reservation
-> refresh TTL reservation + tất cả lock key trong reservation
-> update seat map
```

Order thành công:

```text
-> Booking Service gọi Seat Service confirm reservation
-> Seat Service check reservation còn sống
-> đổi các ghế trong seat map sang Sold
-> delete reservation key
-> delete các lock key
```

Cancel/hết hạn/payment fail:

```text
-> lấy reservation
-> delete các lock key
-> đổi seat map về Available
-> delete reservation
```

Một lưu ý nhỏ: nếu reservation hết TTL tự mất, bạn vẫn cần cơ chế cleanup seat map. Có 2 cách:

```text
A. Redis keyspace notification: nghe event expired của reservation/lock rồi update seat map
B. Lazy cleanup: khi get seat map, nếu ghế Locked nhưng lock key không còn thì tự coi là Available và sửa lại cache
```

Với hệ thống học microservice, mình khuyên bắt đầu bằng **lazy cleanup**, đơn giản và dễ debug hơn. Sau đó nâng cấp sang keyspace notification/background worker khi muốn realtime sạch hơn.




cách trên có tối ưu không, khi lên production, khi mà phim có tới hàng trăm xuất chiếu, và dữ liệu ghế lên tới hàng hàng, và có thể có thể hàng triệu người cùng nhấp nhả nghế ?


Có thể lên production được, nhưng **chưa phải tối ưu nhất nếu mọi thao tác đều update cả seat map hash và nhiều key riêng lẻ một cách rời rạc**. Kiến trúc 3 loại key là đúng, còn production cần siết thêm vài điểm.

Với scale lớn, nên nghĩ như này:

```text
showtime:{showtimeId}:seats        -> read model để render sơ đồ ghế
lock:showtime:{showtimeId}:seat:x  -> chống trùng ghế, TTL ngắn
reservation:{reservationId}        -> gom ghế user đang giữ
```

Cái này ổn vì **dữ liệu được shard tự nhiên theo showtimeId**. Hàng trăm suất chiếu không đáng sợ bằng một suất chiếu hot có 50.000 user cùng bấm vào cùng vài ghế đẹp. Bottleneck thật nằm ở những ghế/suất chiếu hot, không nằm ở tổng số suất chiếu.

Điểm cần tối ưu khi production:

**1. Không đọc/ghi toàn bộ sơ đồ ghế mỗi lần user click**

Seat map có thể là Redis Hash:

```text
showtime:{showtimeId}:seats
field: A1 -> json/status
field: A2 -> json/status
```

Khi lock A1 thì chỉ update field A1, không serialize lại cả map.

**2. Per-seat lock bằng `SET NX EX` là rất tối ưu**

Redis xử lý lệnh này cực nhanh. Với race condition, đây là hướng đúng:

```text
SET lock:showtime:1:seat:A1 reservationId NX EX 600
```

Ai thắng thì giữ ghế. Ai thua thì báo ghế vừa được người khác chọn.

**3. Dùng Lua script cho thao tác nhiều bước**

Khi thêm ghế, bạn cần làm nhiều việc:

```text
check reservation còn sống
check seat lock chưa tồn tại
set lock key
add seat vào reservation
refresh TTL
update seat status
```

Nếu làm từng command C# riêng lẻ thì có thể bị trạng thái nửa chừng. Production nên gom vào Lua script để atomic.

**4. Reservation không nên lookup theo user bằng scan**

Không làm kiểu:

```text
SCAN reservation:* rồi tìm userId
```

Cái này chết khi scale lớn.

Nên key trực tiếp:

```text
reservation:showtime:{showtimeId}:user:{userId}
```

hoặc có index:

```text
user:{userId}:active-reservation:{showtimeId} -> reservationId
```

Như vậy lấy ghế user đang giữ là O(1).

**5. Seat map realtime không nhất thiết phải “chuẩn tuyệt đối từng millisecond”**

Seat map là read model. Lock key mới là source chống race. UI có thể gần realtime qua SignalR/WebSocket:

```text
SeatLocked event -> push A1 locked
SeatReleased event -> push A1 available
SeatSold event -> push A1 sold
```

Nếu UI chậm vài trăm ms cũng không sao, vì khi user click ghế, backend vẫn check lock key bằng `SET NX`.

**6. Không nên tạo quá nhiều background cleanup nếu chưa cần**

TTL key tự hết hạn là tốt. Nhưng seat map có thể stale. Production có thể dùng kết hợp:

```text
Lazy cleanup khi get seat map
+ background worker nhẹ
+ Redis keyspace notification nếu cần realtime hơn
```

**7. Hot showtime cần rate limit và debounce**

Nếu hàng triệu người “nhấp nhả ghế”, bottleneck có thể đến từ hành vi click liên tục. Nên có:

```text
rate limit theo userId/IP
debounce frontend
giới hạn số ghế/user/showtime
không cho lock/unlock liên tục quá nhanh
```

**Kết luận:** kiến trúc 3 key của bạn là đúng và có thể production hóa. Nhưng để tối ưu thật sự, bạn nên coi:

```text
lock key = source of truth cho quyền giữ ghế
reservation key = source of truth cho giỏ ghế đang giữ
showtime seat map = read model/cache để render nhanh
```

Và các thao tác lock/add/release/confirm nên được atomic bằng Lua script hoặc transaction cẩn thận. Với cách đó, kể cả nhiều suất chiếu và lượng click rất lớn, Redis vẫn gánh tốt hơn nhiều so với việc đẩy toàn bộ trạng thái xuống database mỗi lần user bấm ghế.
